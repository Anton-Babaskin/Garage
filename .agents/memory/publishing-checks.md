---
name: Проверка публикации
description: Как не повторять неверные выводы при диагностике подключения базы и старой страницы 404.
---

Не считать наличие runtime-managed секрета DATABASE_URL доказательством существования production-базы. Проверять production отдельным read-only запросом через штатный инструмент.

**Why:** В этом проекте проверка секретов показывала DATABASE_URL, но запрос к production возвращал «This project has no production database». Создание пустой таблицы в development не устранило ошибку разрешения имени базы. Предположение, что достаточно создать таблицу и повторить публикацию, привело к повторным безрезультатным рекомендациям.

**How to apply:** При ошибке подключения сначала подтвердить существование production-базы. Если её нет, сверить с актуальной документацией настройку Create production database в Publishing. Не копировать development connection string и не обещать, что обычный Republish создаст базу без этой настройки.

Отдельно диагностировать последнюю успешную публикацию и новую неудачную попытку.

**Why:** После падения новой версии пользователю продолжала отвечать старая шаблонная сборка с 404. Страница по публичной ссылке не отражала уже подготовленный Node.js-сайт.

**How to apply:** Сопоставлять историю сборок с логами конкретной revision. Не переделывать сайт и не восстанавливать шаблонные приложения ради устранения 404 старой сборки.
